Mechanism: betswirl-chainlink-vrf-v2.5

HMAC-SHA256 used Yes
EvidenceBetSwirl's dice contract does not use SHA-256 at all in the outcome derivation — the VRF word is mapped to an outcome purely via modulo arithmetic. There is no SHA-256 concatenation and therefore no length-extension attack surface. Our implementation wraps individual rolls in HMAC-SHA256, which is also secure.

CSPRNG used Yes
Generator nameChainlink VRF v2.5 (BLS-based verifiable random function)
Approved construction Yes
EvidenceChainlink VRF v2.5 uses an elliptic-curve VRF backed by the oracle's BLS key. The output is verifiably unbiased and unpredictable without the oracle private key. This is a stronger construction than a software CSPRNG.

Generated client-side No
EvidenceBetSwirl has no player-supplied client seed. Our implementation substitutes the consumer contract address as client_seed. The randomness query input is entirely controlled by the on-chain coordinator, not the player.

Evidence category1.0
DescriptionThe VRF request transaction is committed on-chain before Chainlink responds with randomness. The requestId and block number are permanently recorded on Ethereum/Sepolia. The sequence of events is independently verifiable via a block explorer.

Threat ActorResistedReasoning
Dishonest Operator PASS The operator submits a VRF request and cannot predict or choose the returned random word — it is produced by Chainlink's oracle using a key the operator does not control. The server seed for our HMAC session is derived directly from this VRF output.
Malicious Player PASS Players have no input into the randomness. There is no client seed they can craft to influence the VRF output. The contract controls the query input entirely.
External Eavesdropper PASS The VRF word is only revealed after the request is fulfilled on-chain. HMAC-SHA256 is used for per-roll derivation, which is computationally secure. Observing past outputs does not reveal the HMAC key.
Compromised Oracle FAIL If the Chainlink oracle node's private key is compromised, an attacker could generate valid-looking VRF proofs for chosen outputs. This is a known, documented trust assumption of all VRF-based systems.
