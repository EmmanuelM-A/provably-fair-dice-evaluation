Non-Programmable Checks

Mechanism: hmac-sha256

HMAC-SHA256 used Yes
EvidenceStake explicitly uses HMAC-SHA256 with the server_seed as the key and '{client_seed}:{nonce}:{cursor}' as the message. This is documented on their provably fair page. No bare SHA-256 concatenation is used at any stage of the outcome derivation.

CSPRNG used Yes
Generator nameos.urandom (OS-level CSPRNG)
Approved construction Yes
EvidenceServer seeds are generated via os.urandom(32), which draws from the OS kernel's CSPRNG (/dev/urandom on Linux, CryptGenRandom on Windows). This is an approved construction per NIST SP 800-90A and is not susceptible to state reconstruction attacks.

Generated client-side No
EvidenceStake generates a random default client seed server-side on the player's behalf. Players can replace it with any value they choose via the UI, but the default is not player-generated. This gives Stake the technical capability to know the default client seed before it is used.

Evidence category0.0
DescriptionStake publishes the SHA-256 hash of the server seed before play begins, but this commitment exists only on Stake's own servers. There is no on-chain timestamp, no third-party certificate, and no external record to independently confirm the hash was published before the player's client seed was received. Trust in the ordering of events is entirely based on Stake's word.

Threat ActorResistedReasoning
Dishonest Operator FAIL The server seed commitment is self-reported by Stake with no external verification. A dishonest operator could in principle wait to see a player's client seed before selecting and committing a server seed. There is no independent mechanism to prove the commitment preceded the client seed submission.
Malicious Player PASS The server seed is unknown to the player at bet time — only its SHA-256 hash is shown. Without the pre-image, the player cannot compute outcomes for any client seed or nonce combination, regardless of what client seed they choose.
External Eavesdropper PASS HMAC-SHA256 is computationally secure. An eavesdropper observing the published outcome cannot derive the server seed key from the HMAC output.
Compromised Oracle PASS No external oracle is used. Stake generates all randomness internally via os.urandom. There is no oracle attack surface — though this shifts all trust to Stake's own infrastructure security.

Reseeding frequencyper_session
Entropy source qualitystrong
Entropy independent of PRNG state Yes
EvidenceA fresh server seed is drawn from os.urandom(32) at the start of each session. os.urandom pulls entropy from the OS kernel pool, which is independent of the HMAC derivation state. Knowing the current session's outcomes tells an attacker nothing about the next session's server seed.

Uses one-off seeds per round No
Shared state update formally documented Yes
Shared state update provably one-way Yes
EvidenceAll rolls within a session share the same HMAC key (server_seed). HMAC-SHA256 is formally specified in FIPS 198-1 as a provably one-way MAC construction. Knowing any roll's raw_output does not allow an attacker to recover the server_seed or compute other rolls. Once the server_seed is disclosed post-session, all that session's outcomes become computable — this is intentional and necessary for player verification.

Evidence: Stake's published algorithm starts the nonce at 0 and increments by 1 for every bet within a session. When a player requests a new server seed, the nonce resets to 0 alongside a fresh server_seed — this counts as seed rotation so the (server_seed, client_seed, nonce) triple remains unique. Stake does not document what happens if the nonce reaches the maximum integer value.
